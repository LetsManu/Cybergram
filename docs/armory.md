# Armory v2: recipes, gear, guides and the shop

This is the working guide for Cybergram's Armory (protocol 22): the shop where
heroes spend Lumen. It covers item data, recipes, build guides, the
recommendation rules, bots, the shop screen, Item Sets, the balance check and
debugging. The design is `design/gdd/items-and-armory.md` (canon); the plan and
owner decisions are `docs/plans/armory-v2-recipes-gear.md`. The v1 tiered
Armory (mounts with tiers I-III, `ArmoryPanel`, `ShopModel`, `Armory.buy`) was
removed at the v2 switch-over; its history is in `docs/balance/armory-review.md`.

| Piece | File | Runs on |
|---|---|---|
| Items | `ArmoryItemDef` in `assets/data/economy/armory_catalog_v22.tres` (generated) | both |
| Recipe prices | `RecipeMath` (`src/gameplay/progression/recipe_math.gd`) | both |
| Equipment | `ItemInventory` (3 sockets, Chamber, 6 open slots, visit log) | server (replicated) |
| Purchase rules | `ItemShop` (`item_shop.gd`), called by `ProgressionSystem` | server only |
| Signature passives | `SignaturePassives` + `SignatureRulesDef` (`signature_rules.tres`) | server |
| Build guides | `RecommendedBuildDef` + `BuildNodeDef` in `recommended_builds_v22.tres` (generated) | both |
| Recommendations | `BuildAdvisor` + `BuildState` (`src/gameplay/progression/`) | client (shop) and server (bots) |
| Rule tuning | `AdviceRulesDef` in `advice_rules.tres` | both |
| Data checks | `ArmoryValidator`, run by `tests/unit/economy/armory_validator_test.gd` | tests |
| Shop screen | `ItemShopModel` (logic) + `ItemShopPanel` (drawing, input) in `src/ui/hud/` | client |
| Item Sets | `CustomBuildStore` + `BuildsViewModel` | client, `user://builds.json` |
| Visuals | `ArmoryVisualsData` (`assets/data/visuals/armory_visuals.json`, generated by `tools/art/gen_armory_visuals.py`) | client |

The server is authoritative. The client only sends a request; the server checks
every rule and answers with a `HeroProgress.Result`.

## Equipment model

- **Gun sockets:** Core, Barrel, Frame, each holding one finished weapon part
  (a Crystal on Mana guns, a Chip on Mechanical guns: the same item id, shown
  by `chip_name` / `display_name`).
- **Chamber:** one Ammo Type and one Ammo Mod (6 types, 5 mods).
- **6 open item slots:** loose components, gear Assemblies, gear Signatures.
  Any of these fits any slot. A second copy of a component is a spare and gives
  no stats until the first is gone.
- **Squad upgrades and Med-Packs** use their own row, not a slot (carry 3).
- **Tiers:** Component (250-400) -> Assembly (800-1,000, two components plus a
  combine cost) -> Signature (2,400-2,550, an Assembly plus parts plus a combine
  cost, one named passive). A hero owns **at most 2 Signatures** and **one copy
  of any item id**. There are 14 Signatures: 8 on the gun, 6 body gear.
- **Price of a recipe item** = combine cost + the price of the parts you do not
  own yet. `RecipeMath.total()` is the full price; `RecipeMath.resolve()` says
  which owned parts a buy uses up.
- **Selling** pays 60% of the recipe total (rounded down to 5). Anything bought
  during the current visit can be undone for 100%, one item at a time or with
  Undo last. An undo is blocked while a later purchase used one of its parts.
- The visit ends when you leave the zone or die. You can shop only in your own
  HQ zone and only while alive.

Catalog order is the wire id and is **append-only from v22 on**
(`item_shop_wire_test` pins it): 0 Med-Pack, 1-8 squad upgrades, 9-18
Components, 19-28 Assemblies, 29-42 Signatures, 43-48 Ammo Types, 49-53 Ammo
Mods. 54 items, all below 128; squad upgrades must stay below 32
(`ProgressState.owned_bits`).

## Wire contract (protocol 22)

- **Requests:** `ACTION_BUY` arg is the catalog index (the old `tier << 8` byte
  is ignored). `ACTION_SELL` arg is an inventory place (`ProgressState.INV_LOCS`)
  to sell; `UNDO_ITEM_FLAG | place` undoes the purchase that put an item there;
  `UNDO_ITEM_FLAG | UNDO_ROW_FLAG | index` undoes a squad upgrade or Med-Pack;
  `UNDO_LAST` reverts the last change of the visit.
- **Results:** every request bumps `ProgressState.shop_seq` and sets
  `shop_result`; the panel shows the exact reason (`ItemShopModel.result_key`).
- **Replicated state:** `inv_items` (3 sockets, 2 Chamber ids, 6 slots, a spare
  flag per slot), `inv_undo_bits`, `visit_owned_bits`, `visit_medpacks`,
  `signals` (the `SIG_*` bits for the advisor). Other players' builds are
  replicated publicly (scoreboard, death card, model).
- The `mount_*` fields and `HeroProgress.mounts` are v1 leftovers: empty in
  matches, kept only because the wire format carries them.
- A protocol 21 client is refused at login: **everyone must update**.

## Adding an item

1. **Design first.** Add the item to `design/gdd/items-and-armory.md` (§3.5
   tables, marked [TUNE] until tested) and `design/registry/entities.yaml`.
   Keep prices in their band: Component 250-450, Assembly 800-1,100, Signature
   2,400-3,200 (gear Signature combine <= 900).
2. **Add the row** to the item tables in `tools/armory/build_catalog.py`
   (`ITEMS`; **append at the end**: the order is the wire id). Fill `id`, name,
   kind, tier, `recipe` (part ids, an id may repeat), `combine_cost`, stats
   (`stat_ids` / `stat_ops` / `stat_values`, plus the `mech_*` set when a Mech
   gun differs), `passive`, `body_anchor` and the guide fields (`category`,
   `tags`, `counter_tags`, `keywords`, `phase`, `explain_key`).
   Squad upgrades, Med-Pack and Ammo keep their v1 property blocks, frozen in
   `tools/armory/legacy/armory_catalog_v1.tres.txt`.
3. **Regenerate:** `python3 tools/armory/build_catalog.py`. Never hand-edit the
   `.tres`.
4. **Text and icons:** an English line for `explain_key` (and name / effect keys
   if used) in `assets/localization/hud.csv`; a glyph in
   `src/ui/hud/shop_icons.gd`; visuals through `tools/art/gen_armory_visuals.py`
   (gun part or body anchor).
5. **A Signature passive** needs its id in `SignaturePassives`, its numbers in
   `signature_rules.tres` and a test in `tests/unit/combat/signature_passives_test.gd`.
6. `$GODOT --headless --path . --import`, then the economy tests (see Testing).
   The validator checks: recipe DAG with no cycles, `Total = combine + parts`,
   tier price bands, gear Signature combine <= 900, every component feeds at
   least two finished items, caps (HP +200, gear armor / resist 0.20, CDR 0.25,
   penetration 0.60), index limits, body anchor or socket on every item.

## Build guides

A `RecommendedBuildDef` is a guide: `nodes` holds `BuildNodeDef`s. Each node
names a **finished item** (plus `alternatives`, so 2-3 choices); the advisor
works out the parts and picks the choice closest to done.

| Field | Meaning |
|---|---|
| `id` | Unique in the build; other nodes name it in `requires` |
| `item_id`, `target` | Own this item (count for Med-Packs) |
| `section` | OPENING, EARLY, SPIKE, CORE, SQUAD, CONSUMABLE, DEFENSIVE, OFFENSIVE, UTILITY, COUNTER, LATE |
| `priority` | Higher means sooner. A bot **saves** for the top step rather than buying a lower one, so priority order is the buying order |
| `requires` | Nodes that must be done (or no longer block) first |
| `alternatives` | Items that satisfy this node instead |
| `conditions` | Rule ids. If set, the node is situational and only offered while one matches |
| `reason_key` | "Why" text (falls back to the item's `explain_key`, then the section) |
| `core` / `optional` / `fallback` / `skippable` / `keep` / `min_s` / `max_s` / `expert` | See `BuildNodeDef` |

A guide never breaks when the player ignores it: an owned alternative satisfies
its node, an item the hero cannot buy counts as passed, and a recommendation
never blocks a purchase. Old "simple" builds (`item_ids` / `targets`) still
work as a chain of nodes.

**Authoring.** The guides are generated by `tools/armory/build_guides_v22.py`
(never hand-edit the `.tres`). Each hero is one `guide(style, start, core,
barrel, ammo, sig2, mod, gear, squad, tail)` call. Two styles:

- `balanced`: the first squad steps and a gear Assembly come before the Core
  Signature (first Signature 15-19 min, 20-25% squad, about half the full build
  owned at 30:00).
- `gun_first`: the Core Signature first, a short squad list after it (first
  Signature 10-14 min, items up to 80%).

Every guide fills the full build: Core Signature, Barrel and Frame Assemblies,
the Chamber, a second Signature (a gear, Barrel or Frame Signature: the
`sig2` choices decide which), the open slots, a Med-Pack restock step (keeps 3
in the bag) and squad steps. After editing: run the script, `--import`, the
validator test, then the balance report (below).

## Recommendation rules (BuildAdvisor)

**Next part.** For the chosen goal the advisor recommends: the goal itself when
affordable, else the largest affordable missing Assembly, else the cheapest
stat-giving missing component that fits an open slot (never a buy the server
would refuse; with all 6 slots full it does not recommend a loose component).

**Scoring.** A node's score is `priority` plus the bonus of every matched rule
(`AdviceRulesDef.bonus`). Three rules are added automatically: `core_tier_ready`,
`affordable_now` and `counters_enemy`.

| Rule id | Matches when |
|---|---|
| `taking_weapon_damage` / `taking_skill_damage` | Server signal: gunfire or ability damage within `damage_window_s` of at least `damage_threshold_frac` x max HP |
| `died_often` | At least `deaths_threshold` deaths within `deaths_window_s` |
| `low_health` | HP below `low_health_frac` |
| `team_behind` / `team_ahead` | Resonance deficit >= `behind_deficit`, or average level lead >= `ahead_levels` |
| `objective_soon` | The next Surge is within `objective_soon_s` |
| `enemy_<tag>` | At least `enemy_tag_threshold` enemy heroes carry the tag (3v3 uses 1, 5v5 uses 2; a rare trait needs 1); also enemy gear armor from the server signal |
| `team_lacks_sustain` / `team_lacks_frontline` | No allied healer / tank |

`HeroDef.tags` holds threat tags, `HeroDef.roles` holds roles. To add a rule: add
its id to `BuildAdvisor.RULES` and logic to `_rule_matches`; add a `SIG_*` bit
in `ProgressionSystem.refresh_signals` if it needs server state; add the bonus
to `advice_rules.tres`; add `HUD_ADVICE_R_<ID>` to `hud.csv`; add a test in
`tests/unit/economy/build_advisor_test.gd`.

**Debugging a decision.** `BuildAdvisor.evaluate(...).trace` lists every node
offered (score, matched rules, cost), every node skipped (reason) and the pick.

## Bots

Bots shop through the same path as players (`BotBrain._decide_shop`). On the
Armory pad (or in the Sanctum) a bot builds a `BuildState` from its server
wallet and both teams' heroes, asks `BuildAdvisor` for its hero's guide
(`recommended_builds_v22.tres`) and sends the next part as `ACTION_BUY`. When
all 6 slots are full and the next step needs one, it sells the loose item of
lowest value that its plan never uses. It saves for the top step. It
re-evaluates only when Lumen, purchases, Med-Packs or the advice signals
change, so a refused request is not repeated. Each purchase is logged in the
bot log (`t<tick> h<id> buy <part> for <goal> (<node>)`). Tests:
`tests/integration/bots/bot_match_test.gd`.

## Shop UI

`ItemShopPanel` (full-width modal, designed on 1600 x 900 and scaled; 720p and
1080p use the same layout) with three tabs:

- **Recommended:** NEXT PURCHASE card (the advisor's part, can-afford chip,
  reason), the BUILD PATH graph (done ticked, current highlighted, choices) and
  up to 3 SITUATIONAL cards with a short reason.
- **All Items:** stat filters on the left, the grid by shelf (Components,
  Assemblies, Signatures, Ammo, Squad, Consumables), and on the right the recipe
  tree with owned parts ticked, "builds into", the stat gain and the passive.
- **Item Sets:** the player's own sets (below).

The bottom strip is always on screen: Lumen with its income, the gun sockets
and Chamber, the 6 open slots, Signatures n/2, Med-Pack and squad chips, Sell
and Undo last. Keys: F / interact or B opens on the pad, Esc closes; Q / E or
LB / RB switch tabs; Enter / A buys the next part of the focused goal;
Backspace / X sells or undoes the focused item; Ctrl+Z / R3 Undo last; R / L3
jumps to the advisor's next buy; `/` or Ctrl+F searches. Mouse: click focuses,
double-click buys, right-click on a loadout slot sells or undoes. The toast
shows the exact server result. The pad waypoint (`ArmoryWaypoint`) shows while
you can afford something and are off the pad.

## Item Sets (private, on this PC)

Item Sets are the old "My builds", renamed. They live in `user://builds.json`
(`CustomBuildStore`, file version 2) and never reach a server.

- A set is a build of finished items for one hero. The set in use replaces the
  hero guide in Recommended and drives the same `BuildAdvisor`.
- Keys on the tab: Enter / A use; N / L3 new from the guide; D / R3 duplicate;
  Delete / X twice deletes; C copies a `CGB2:` string, V pastes one (only sets
  for this hero). In All Items, + / RT adds the focused item to the set in use.
- Warnings never delete: unknown items, a count the item does not have, an item
  that is switched off, unknown alternatives are listed under the set.
- Old files stay readable: version 1 builds load as old-Armory builds, are kept
  on save, and are not listed or followed by the v2 shop. `CGB1:` strings are
  refused with "Made for the old Armory".
- Not built yet: rename and notes have store calls (`rename`, `set_notes`) but
  no text field in the panel.

## Balance check

`tools/balance/armory_report.gd` spends every hero's guide along the
weak / average / strong Lumen curves (wardlings-and-economy.md §18; the model in
`tests/unit/economy/economy_curve_test.gd`) through the bot path
(`BuildState.from_hero`, `BuildAdvisor.best()`, `ItemShop.buy`, selling a loose
item when slots are full). One Med-Pack is used every 210 s.

```
$GODOT --headless --path . -s res://tools/balance/armory_report.gd            # about 3 min, writes docs/balance/armory-v2-report.md
$GODOT --headless --path . -s res://tools/balance/armory_report.gd -- --quick  # average curve, pad only, about 30 s, prints only
```

It reports per hero, profile and visit pattern: first Signature, full-build
value, share owned at 30:00, unspent Lumen, spend split (items / squad /
consumables), dead zones over 240 s and sells; then when the strong curve with no
squad spend completes the full build, and the items no guide names or no run
buys. It only observes. The reading, targets and changes are in
`docs/balance/armory-v2-review.md`. Canon values change through the GDD and
`design/registry/entities.yaml` first; prices live in `tools/armory/build_catalog.py`.
Re-run it after changing prices, items or guides.

  a sample build and opens the shop. `--debug-armory-catalog` opens All Items;
  `--debug-armory-builds` opens Item Sets with a sample set (in memory only).
  `RESOLUTION=1920x1080` renders at 1080p. Run `--import` first after editing
  `hud.csv`. Evidence is kept in `production/qa/evidence/armory-v2-shop/`.
- The server writes one OpsLog line per request (`armory.buy`, `armory.sell`,
  `armory.undo`, `armory.reject` with the result name; hero net id only, never
  account data), switched by `ProgressionSystem.armory_log`. Lumen spent is in
  `HeroProgress.spent_lumen`.

  shows every item on a hero.
