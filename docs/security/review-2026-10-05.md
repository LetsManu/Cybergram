# Cybergram security review, 2026-10-05 (W11-Q1)

Scope: accounts (`src/networking/auth/`), transport (DTLS), protocol codecs,
the launcher update path, server and Docker. Reviewer: security-engineer (Q1, Wave 11).
Severity scale as in `/security-audit`. Cybergram is multiplayer, so every
finding that rates HIGH on the base table is reported as **Critical**.

Status values: **Fixed** (commit given) or **Open** (with a proposed fix).

## Findings

### SEC-001 Critical: account session token sent in clear text after a forced downgrade

- **Category:** transport / session management
- **Where:** `src/ui/menu/main_menu.gd` `_fall_back_to_plain()` -> `_with_session()`
  (before the fix: the `OP_RESUME` sends in `_with_session`, `_resume_from_launcher`
  and the lobby-leave handler).
- **Description:** when the DTLS handshake never completes, the game retries in
  plain UDP and marks the host plain for the rest of the process. The login
  screen correctly hides login/register on a plain link (`LoginScreen` with
  `accounts_available = false`; the launcher's `LoginSession.login()` refuses
  too), so a **password** is never sent in plain text. But the game re-sent the
  held **session token** (`OP_RESUME`) on the plain link. A launcher hand-over
  always holds an account token.
- **Attack:** an on-path attacker (public Wi-Fi, a compromised router) drops the
  DTLS handshake packets to UDP 7777. The game falls back to plain UDP and sends
  the account token in clear text. The server (which does have a certificate)
  never sees that plain link, but the attacker now owns a valid bearer token:
  they open their own DTLS connection and `OP_RESUME` it inside the 60 s grace,
  then export the victim's data (friends, profile), change the profile, and
  manage friends and blocks as the victim. Password change and delete still need
  the password.
- **Fix:** `MainMenu.may_send_token(link_secure, guest)`. An account token is only
  sent on a DTLS link; guest tokens (no account) may still resume on a guest-only
  server. `session_guest` remembers which kind is held. Test:
  `tests/unit/security/security_review_test.gd`.
- **Owner action:** none.

### SEC-005 Medium: `--dtls-insecure` honoured in release builds

- **Where:** `src/networking/auth/auth_config.gd` `parse()` (`--dtls-insecure`).
- **Attack:** a phishing "fix your connection" shortcut tells players to add
  `--dtls-insecure`; their client then accepts any certificate and an attacker
  with a self-signed certificate reads their password.
- **Fix:** the flag only takes effect when `OS.is_debug_build()`; release exports
  ignore it with a warning. Launcher copy synced. Test: `test_sec005_*`.
- **Owner action:** none. Always export players' builds as release (no
  `--export-debug`).

### SEC-002 Critical (High on the base table): login limiter bypass and victim lockout

- **Category:** authentication / brute force, denial of service
- **Where:** `src/networking/auth/account_service.gd` `_login()`, `_finish()`,
  `_account_op()`, `_finish_verified()`; `src/networking/transport/enet_transport.gd`
  (`_next_id` gives every connection a new peer number).
- **Description:** the per-connection limiter was keyed on the ENet peer number
  (`"p:%d"`), which is new on every reconnect, so it limited nothing. The only
  real limit was per account (5 failures / 5 min -> 5 min lock), and anyone
  could trigger it.
- **Attack (a):** a guesser reconnects after every 4 tries and is only slowed by
  the account lock: about 1 400 guesses per account per day, from one machine.
  **Attack (b):** a griefer sends 5 wrong passwords for a streamer's username
  every 5 minutes and the streamer cannot log in at all.
- **Fix:** `Transport.peer_address()` (ENet: the remote IP). Limits are now per
  source IP (`max_failures_per_peer`, 10) and per (account, source IP)
  (`max_failures_per_account`, 5). A stranger's failures no longer lock the
  owner out from their own address, and reconnecting does not reset anything.
  Expired entries are purged every minute (was: once a day), because they now
  hold an IP address. `PRIVACY.md` updated to say so.
- **Residual risk:** a botnet with many IPs still gets 5 guesses per IP per
  5 min; players behind one NAT / carrier-grade NAT share the per-IP budget.
  Next step if abuse shows up: a global per-account soft limit with an
  exponential delay instead of a hard lock.
- **Tests:** `tests/integration/auth/security_review_service_test.gd`
  (`test_sec002_*`).
- **Owner action:** none. Note the new paragraph in `PRIVACY.md` ("After a failed
  login") before you publish it.

### SEC-003 Medium: password change kept other sessions alive

- **Where:** `account_service.gd` `_finish()` (second stage, op `-1`).
- **Attack:** a player who notices someone else is using their account (for
  example via a token stolen as in SEC-001, or a login left open on a friend's
  PC) changes the password, but the other session keeps working for as long as
  it stays connected, and can be resumed for the grace period after.
- **Fix:** `end_other_sessions(account_id, keep_peer)` after a successful change.
  Test: `test_sec003_password_change_ends_other_sessions`.
- **Owner action:** none.

### SEC-004 Medium: PBKDF2 work factor is low, and never upgraded

- **Where:** `assets/data/net/auth_rules.tres` (`pbkdf2_iterations = 60000`),
  `account_service.gd` `_finish()` (login does not re-hash).
- **Description:** OWASP (2023) recommends 600 000 iterations for
  PBKDF2-HMAC-SHA256. 60 000 is a tenth of that. The PBKDF2 is pure GDScript on
  a NAS CPU, so raising it costs real login latency. Constant-time compare
  (`Pbkdf2.constant_time_equals`) and the dummy hash for unknown usernames are
  correct; salts are 16 random bytes per account.
- **Attack:** if the `/data` volume leaks (a backup copied to a cloud folder),
  each password can be guessed offline 10x faster than recommended.
- **Proposed fix (open):** (1) measure one hash on the NAS
  (`Pbkdf2.derive` with 600 000) and raise `pbkdf2_iterations` as far as a ~0.5 s
  login allows; (2) on a successful login, if the stored `iterations` is below
  the rule, re-hash the (just verified) password with a new salt and save it,
  so old accounts upgrade on their next login. Item (2) is about 15 lines in
  `_finish()`; it was not done here because the right number needs a
  measurement on the real NAS.
- **Owner action:** run the measurement on the NAS, then pick the number.

### SEC-006 Low: account files used the default file mode

- **Where:** `src/networking/auth/file_account_store.gd` `open()` / `put()`.
- **Description:** account files (with password hashes) were created with the
  process umask (usually 0644: world-readable) inside the data volume.
- **Attack:** any other user or container with access to the NAS share can copy
  the hashes and crack them offline (see SEC-004).
- **Fix:** directory 0700, files 0600 (Unix only). Test:
  `test_sec006_account_files_owner_only`.
- **Owner action:** for files that already exist, run once on the NAS:
  `chmod 700 <data>/accounts && chmod 600 <data>/accounts/*.json`
  (the store rewrites a file's mode only when it saves it next).

### SEC-007 Low: look-alike usernames

- **Where:** `account_service.gd` `valid_username()`, `PlayerProfile.validate_name()`.
- **Description:** usernames are ASCII `a-z A-Z 0-9 _ - .` only and unique
  case-insensitively, so Unicode homoglyphs and case tricks are already blocked.
  ASCII look-alikes are not: `aIice` (capital i) and `a1ice` can sit next to
  `alice`. Display names are not unique by design; the `#TAG` after a name is
  what tells players apart.
- **Attack:** a scammer registers `Dj8oeck` and asks the owner's friends for
  their password "to fix the server".
- **Proposed fix:** at registration only, compare a "skeleton" (lower-case, then
  `0->o`, `1/i/l->l`, `5->s`, `rn->m`, drop `_ - .`) against a skeleton index in
  `FileAccountStore`, and refuse with `E_NAME_TAKEN`. Login stays exact. Also
  reserve names such as `admin`, `cybergram`, `djboeck`, `support` via the
  name filter data.
- **Owner action:** decide whether to reserve your own name now (add it to the
  name filter in `assets/data`).

### SEC-008 Low: export without re-entering the password

- **Where:** `account_service.gd` `_account_op()` `OP_EXPORT`.
- **Description:** a valid session (DTLS link, logged in) can export the account.
  The export contains no password hash or salt, only the profile, friend/block
  lists and dates. Delete and password change correctly re-check the password.
- **Attack:** whoever holds a session (see SEC-001, now fixed) can read the friend
  list. Limited impact.
- **Proposed fix:** require the password for `OP_EXPORT` (protocol change, so
  bump `PROTOCOL_VERSION`). Not done in this chunk to keep the protocol stable.

### SEC-009 Low: username enumeration (accepted)

- **Where:** `_validate_new()` (`E_NAME_TAKEN`), `_friend_request()` (`E_NOT_FOUND`).
- **Description:** login does not reveal whether a username exists (a dummy hash
  keeps timing equal), but registration and friend requests do. This is
  inherent to unique usernames and friend-by-name. Recorded, no change advised.

## Areas reviewed with no finding

- **Session tokens:** 32 bytes from `Crypto.generate_random_bytes` (CSPRNG),
  memory only, refused when attached to another connection, expire 60 s after
  the connection drops; account tokens are refused on a non-DTLS server.
  Bearer tokens are replayable by design within the grace; SEC-001 was the way
  one could leak, now closed.
- **Constant-time compare** (`src/core/auth/pbkdf2.gd:46`): correct. Unknown
  usernames hash with a dummy salt, so timing does not reveal existence.
- **Delete authorisation:** password re-checked, rate limited, cascade removes the
  id from all other accounts, sessions and presence.
- **File store paths:** file names come only from server-generated 32-hex ids
  (`is_hex_id`), checked again against the file name at load; usernames never
  reach a path. Corrupt or foreign JSON is skipped with a warning that shows only
  8 characters of the file name. Leftover `.tmp` files are removed.
- **DTLS:** the client passes the host name to `dtls_client_setup`, so
  `TLSOptions.client()` checks the certificate chain against the system CAs
  *and* the host name. IP addresses and `localhost` default to plain (guest only).
  The downgrade to plain UDP cannot make the client send a password: the game's
  `LoginScreen` disables login/register when `accounts_available` is false
  (`src/ui/menu/login_screen.gd:85`), and the launcher's `LoginSession.login()`
  refuses on an insecure link. The server also refuses login/register with
  `E_NOT_SECURE` when it has no certificate. Residual: an on-path attacker can
  still force guest-only play (a denial of service, inherent to the fallback).
- **Protocol parsing:** `LobbyCodec.Reader` reads only u8/u16/fixed ids with a
  bounds check per read and sets `ok = false` on overrun; strings are capped
  (64 bytes, passwords 128); lists are a u8 count (max 255); every
  client-to-server packet is capped at 1 200 bytes before parsing.
  `InputBatchCodec.decode` checks `count <= max_count` and the exact size.
  `InputCommand.read_from` produces only bounded values: the move vector is
  re-normalised to length <= 1 (no speed hack through input), yaw is a u16
  fraction of a turn, pitch is clamped to +-90 degrees, buttons are masked,
  action ids above the max become `ACTION_NONE`. No sizes come from signed
  fields, so there are no negative lengths or overflowing allocations.
- **Lag compensation:** `view_tick` is clamped to `NetConfig.max_rewind_ms`
  (`hitscan_tracer.gd:122`), so a client cannot rewind further than the limit.
- **Actions:** `ACTION_LEARN` checks skill points, unlocked state, Boost before a
  Fork, a Fork before Mastery, ultimates have no forks; `ACTION_BUY` checks
  alive, at the Armory, funds, carry limits and prerequisites; `debug_shop_anywhere`
  is set only by the practice-range installer, not by any packet;
  `ACTION_SPAWN` choice is clamped.
- **Chat:** `ChatFilter.sanitize` strips control/invisible characters and
  collapses whitespace; the lobby chat log renders with `push_color` + plain
  text, not BBCode, so markup cannot be injected.
- **Account request flood:** a token bucket (12 burst, 3/s) per connection, and
  one PBKDF2 job per connection at a time.
